Deterministic Retrieval with gget & AI

NM

Nasir Mahmood Abbasi, PhD

Bioinformatics Educator

Tested on: Cursor, Aider, Claude Desktop

Learning objectives and prerequisites

By the end of this lesson you will be able to:

  • Install and verify the gget command-line tool and Python package in a reproducible environment.
  • Perform deterministic retrievals from Ensembl and UniProt using gget (both CLI and Python API).
  • Save, record, and present retrieval outputs so they can be passed to a Large Language Model (LLM) or human reviewer instead of asking the LLM to invent facts.
  • Interpret common outputs (IDs, coordinates, sequences) and understand what they do and do not prove.

Prerequisites: basic command-line familiarity (bash or similar), a working Python 3.8+ environment, and permission to install Python packages. No prior knowledge of gget or the Ensembl/UniProt APIs is required.

Why deterministic retrieval matters in bioinformatics

Large Language Models (LLMs) are powerful at synthesizing text and generating code, but they are not authoritative sources of changing biological facts such as current Ensembl gene IDs, transcript coordinates, or canonical UniProt accessions. These facts change over time: annotations are updated, assemblies are remapped, and IDs may be deprecated. Handing an LLM a deterministic, programmatically retrieved record from a primary database before asking it to analyze or write code prevents hallucinations and provides an auditable provenance trail.

gget is a small tool designed to query authoritative bioinformatics resources (Ensembl, UniProt, NCBI, AlphaFold DB, ARCHS4, Enrichr) and return structured results you can save. The workflow we teach here separates retrieval (deterministic, reproducible) from interpretation (LLM or human). Save the raw retrieval responses, the command used, and the retrieval timestamp so downstream analyses can be reproduced and validated.

Reproducible, sequential workflow

The following workflow is structured so you first confirm retrieval works locally, then save and validate outputs, then hand those saved files to an LLM for interpretation. All commands assume a Unix-like shell. Replace species and identifiers as needed.

1) Create an isolated environment and install gget

Files you should have after this step: the virtual environment directory (.venv) and the installation record commands-output.txt.

# Create and activate a Python virtual environment
python3 -m venv .venv
source .venv/bin/activate

# Upgrade pip and install a pinned gget version for reproducibility
python -m pip install --upgrade pip
python -m pip install "gget==0.28.6"

# Verify installation and save the help output
gget --help > retrieval-results/gget-help.txt 2>&1
echo "gget version and help saved to retrieval-results/gget-help.txt"

What these commands produce:

  • .venv/ — isolated Python environment (do not delete if you want reproducibility).
  • retrieval-results/gget-help.txt — contains the list of gget subcommands (info, seq, search, enrichr, archs4, alphafold, etc.).

Note: pin the version number after you confirm behavior (here we used 0.28.6 as an example). If you are reproducing this tutorial at a later date, choose and record the specific version you used.

2) Prepare a retrieval-results directory and record metadata

# Make a directory to hold raw retrievals and logs
mkdir -p retrieval-results
# Record the environment and Python package list for provenance
python -m pip freeze > retrieval-results/requirements.txt
date --iso-8601=seconds > retrieval-results/retrieval_timestamp.txt
echo "Command: gget --help" >> retrieval-results/retrieval_timestamp.txt

Files created:

  • retrieval-results/requirements.txt — exact package versions installed.
  • retrieval-results/retrieval_timestamp.txt — timestamp and basic provenance for the run.

3) Deterministic retrieval: get Ensembl gene metadata using gget info

Example goal: fetch authoritative Ensembl metadata for the human gene FOXP3. Save the raw output and a CSV excerpt for quick human reading.

# CLI: write JSON output of gget info to a file
gget info FOXP3 --species human --format json > retrieval-results/FOXP3_ensembl_info.json

# Python: read, inspect and write a CSV summary using the gget Python API
python - <<'PY'
import json, csv
from pathlib import Path

p = Path("retrieval-results/FOXP3_ensembl_info.json")
data = json.load(p.open())
# gget.info returns a list-like structure; adapt depending on actual shape
# Here we extract commonly useful fields safely
fields = ["query", "ensembl_id", "symbol", "description", "chromosome", "start", "end", "strand", "biotype", "uniprot_id"]
rows = []
for record in data:
    rows.append({f: record.get(f, "") for f in fields})

csv_path = Path("retrieval-results/FOXP3_ensembl_info.csv")
with csv_path.open("w", newline='') as fh:
    writer = csv.DictWriter(fh, fieldnames=fields)
    writer.writeheader()
    writer.writerows(rows)
print("Saved CSV summary to", csv_path)
PY

Files produced:

  • retrieval-results/FOXP3_ensembl_info.json — raw JSON from Ensembl via gget.
  • retrieval-results/FOXP3_ensembl_info.csv — human-readable summary with canonical fields.

4) Deterministic retrieval: download a protein sequence with gget seq

Obtain the protein FASTA for a specific Ensembl ID and save it for downstream analyses (alignment, domain searches, structure prediction). Example uses ENSG IDs or transcript/protein IDs depending on the resource.

# Use gget seq from CLI with an Ensembl gene or transcript ID
# Here we request the canonical protein sequence for ENSG00000141510 (TP53 example).
gget seq ENSG00000141510 --translate true > retrieval-results/TP53_protein.fasta

# Confirm the first line is a FASTA header and the file is non-empty
head -n 1 retrieval-results/TP53_protein.fasta
wc -c retrieval-results/TP53_protein.fasta

Files produced:

  • retrieval-results/TP53_protein.fasta — FASTA-formatted sequence retrieved from Ensembl (or other configured backend).

5) Save exact commands, inputs, and timestamps for provenance

# Append the commands used to a provenance log with timestamps
echo "gget info FOXP3 --species human --format json" >> retrieval-results/commands.log
date --iso-8601=seconds >> retrieval-results/commands.log
echo "gget seq ENSG00000141510 --translate true" >> retrieval-results/commands.log
date --iso-8601=seconds >> retrieval-results/commands.log

Files produced:

  • retrieval-results/commands.log — a small provenance log mapping commands to timestamps.

Output inspection and interpretation

After you save retrieval outputs, inspect them systematically. For each saved file ask:

  • Does the record include authoritative IDs (Ensembl ENSG/ENST/ENSP, UniProt accession)?
  • Are coordinates present, and do they reference a specified assembly (e.g., GRCh38/hg38)?
  • Is there a retrieval timestamp and the gget version recorded?

Example: what to look for in FOXP3_ensembl_info.csv

  • ensembl_id: typically starts with ENSG for genes. If empty, the symbol may be ambiguous or the query matched nothing.
  • chromosome, start, end: numeric coordinates; verify if the record includes an assembly tag. If the assembly is missing, do not assume GRCh38 — consult the Ensembl API response or database documentation.
  • uniprot_id: link to UniProt canonical accessions, if present. Absence does not mean the protein is uncharacterized; it may reflect lacking cross-reference in that release.
  • description: human-readable gene description. Do not treat this as a definitive function annotation; it's a short text string from the database.

What a plausible result means and does not prove:

  • Correct IDs and coordinates indicate the current database mapping at retrieval time. They do not prove that downstream analyses (e.g., variant effect predictions) were performed correctly—those require separate validation.
  • Presence of a UniProt accession means UniProt and Ensembl are cross-referenced in that release; absence could be due to timing or curation differences, not necessarily absence of an actual protein product.
  • Sequence retrieved in FASTA is the sequence the source database considers canonical at that time. It does not guarantee experimental validation or that other isoforms do not exist.

Troubleshooting: symptoms, likely causes, and fixes

Below are common issues when working with gget and how to proceed.

Symptom: gget command not found

  • Likely cause: gget is not installed in the active Python environment or the virtualenv is not activated.
  • Fixes:
    1. Activate the virtual environment: source .venv/bin/activate.
    2. Reinstall: python -m pip install gget==0.28.6 and check python -m pip freeze | grep gget.
    3. Use the full path to the python-installed gget: python -m gget info FOXP3.

Symptom: empty JSON or no matching record for a gene symbol

  • Likely causes:
    • Ambiguous or species-ambiguous gene symbol (e.g., many species use the same symbol).
    • Symbol is deprecated or not present in the selected species.
  • Fixes:
    1. Supply species explicitly: gget info FOXP3 --species human.
    2. Try a stable identifier (Ensembl ENSG...) if available.
    3. Use gget search FOXP3 --species human --format json to see candidate matches and their species context.

Symptom: FASTA file is truncated or contains HTML/redirect text

  • Likely causes: network interruption, API rate limiting, or gget following an HTTP redirect to a page.
  • Fixes:
    1. Check network connectivity and retry.
    2. Inspect the file start with head -n5 to see if it contains an error HTML page; if so, retry later or switch to a different server endpoint if available.
    3. Use the Python API and check for exceptions rather than piping CLI output, so you get proper error messages.

Symptom: different results on repeat retrievals

  • Likely causes:
    • Database updates between retrievals (annotation changes, new releases).
    • Different default assembly or species settings in different runs.
  • Fixes:
    1. Record the gget version and retrieval timestamp; include the Ensembl release or assembly where possible.
    2. If reproducibility is critical, capture and archive the raw JSON output and the complete environment (requirements.txt, Python version).

Limitations, reference-data caveats, and responsible use

Limitations and caveats to keep in mind:

  • Database currency: gget queries live services (Ensembl, UniProt). Results reflect the state of those databases at retrieval time and can change with new releases.
  • Identifier granularity: Ensembl has separate namespaces for genes (ENSG), transcripts (ENST) and proteins (ENSP). Ensure you request the correct namespace for your task.
  • Assembly version: Genomic coordinates are meaningful only when paired with an assembly (e.g., GRCh37/hg19 vs GRCh38/hg38). If the API response omits the assembly, do not assume one—explicitly request or record it.
  • LLM interpretation: providing retrieved records to an LLM reduces hallucination risk but does not eliminate reasoning errors the LLM may make when integrating disparate facts. Always validate critical steps.
  • Data licensing and usage: follow the terms of service and licensing of the upstream databases (Ensembl, UniProt, NCBI, AlphaFold). Some data may have restrictions for commercial use.

Responsible-use notes:

  • When sharing retrieval outputs in publications or reports, include the exact commands, the gget and dependency versions, retrieval timestamps, and the source (Ensembl/UniProt release).
  • Do not assume that a retrieved gene description equals experimentally validated function. Use appropriate experimental evidence when making biological claims.
  • For human genomic data with privacy concerns, ensure that any identifiers or sequences do not inadvertently reveal participant-level data or violate consent agreements.

Next-step checklist

  1. Confirm gget installation and record retrieval-results/gget-help.txt and retrieval-results/requirements.txt.
  2. Run a deterministic retrieval for at least one gene and save both raw JSON and a CSV summary in retrieval-results/.
  3. Record the exact commands and timestamps to retrieval-results/commands.log.
  4. Feed the saved JSON/CSV to your LLM or AI agent as contextual evidence; instruct the agent to cite the saved file when making factual statements.
  5. If you will share results externally, include the gget version, retrieval timestamp, and database release numbers in your methods section.
