Git and GitHub for Bioinformatics

NM

Nasir Mahmood Abbasi, PhD

Bioinformatics Educator

← Previous tutorialAll tutorialsNext tutorial →

Build a small local repository, record a meaningful change, and inspect what Git has captured before deciding whether it is safe to share. The examples use a deliberately data-free project; they do not process sequencing reads or establish that an analysis is scientifically valid.

Before you start

You need a terminal and Git. Check the installation with:

git --version

A GitHub account is optional until you choose to create a remote repository. Work first in a project that contains no patient-level information, credentials, or restricted data. Git records text changes well, but ordinary Git history is a poor home for large sequencing files.

Start a local repository

Create a clean practice directory and initialize it. These commands operate only in your home directory:

mkdir -p ~/projects/omics-demo
cd ~/projects/omics-demo
git init

Git creates a hidden .git/ directory for repository history and settings. At this point it has no tracked project files. Run git status to see the current branch and working-tree state; the exact initial-branch wording depends on your Git configuration.

Describe the project and exclude common local files

A README should tell a collaborator what the repository contains, what inputs it expects, and how to run the analysis. This example documents the practice project without pretending it contains biological results.

cat > README.md << 'EOF'
# Omics demo

A small teaching repository for Git workflows. It contains scripts and configuration,
not raw sequencing data. Add the analysis purpose, required software, input format,
and run instructions before sharing a real project.
EOF

cat > .gitignore << 'EOF'
# Local data and common sequencing files; review project-specific needs
data/raw/
*.fastq.gz
*.bam
*.bai

# Temporary and environment files
*.pyc
__pycache__/
.ipynb_checkpoints/
.env
.env.*
.venv/
envs/
*.key
EOF

Check the ignore rule before adding files: git check-ignore -v data/raw/example.fastq.gz prints the matching rule and its source if the path is ignored. Patterns are project-specific. A broad pattern such as *.bam may hide a small derived file you meant to version, so inspect ignored files rather than assuming all matches are disposable.

Ignore is not deletion or access control. Git ignore rules apply to untracked files. They do not untrack a file already committed, erase it from history, or make a public repository private. If a credential was exposed, revoke or rotate it promptly. Rewriting history requires coordination and may not remove copies in forks or clones.

Make a focused first commit

Stage only the two files you intend to record. Review the staged diff before committing:

git add README.md .gitignore
git status
git diff --cached
git commit -m "Add project README and ignore rules"
git log --oneline -1

git add selects content for the next snapshot; git diff --cached lets you inspect that selection. A commit stores the selected content and a message. The short identifier from git log points to this repository snapshot, not to a result's scientific validity.

Isolate a change on a branch

A branch gives you a separate line of development for a small change. This local example uses main as the stable branch and merges the documentation update back after reviewing it:

git branch -M main
git switch -c docs/input-notes
cat >> README.md << 'EOF'

Input files must follow the format documented with each analysis script.
EOF
git diff
git add README.md
git diff --cached
git commit -m "Clarify input documentation"
git switch main
git merge docs/input-notes
git log --oneline --decorate -3

After the merge, the change is part of main and remains visible in history. If Git reports a conflict, stop and inspect the marked file before continuing; do not discard edits you need. Branching helps organize changes, while review and testing still determine whether they are ready to use.

Add a small script with an explicit input contract

This example reads a tab-separated file with headers named sample and reads. It is a teaching script for checking repository structure; its printed values are whatever the supplied file contains, not an assessment of sequencing quality.

mkdir -p scripts results
cat > scripts/qc_summary.py << 'EOF'
#!/usr/bin/env python3
"""Print sample names and read counts from a two-column TSV."""
import csv
import sys

if len(sys.argv) != 2:
    raise SystemExit("Usage: qc_summary.py samples.tsv")

with open(sys.argv[1], newline="", encoding="utf-8") as handle:
    reader = csv.DictReader(handle, delimiter="\t")
    required = {"sample", "reads"}
    if reader.fieldnames is None or not required.issubset(reader.fieldnames):
        raise SystemExit("Input must have 'sample' and 'reads' header columns")
    for row in reader:
        print(row["sample"], row["reads"])
EOF

chmod +x scripts/qc_summary.py
git add scripts/qc_summary.py
git diff --cached
git commit -m "Add TSV summary example"

For a local smoke test, create a tiny, clearly synthetic samples.tsv with the required header and one made-up row, then run python3 scripts/qc_summary.py samples.tsv. A missing or misspelled header should stop with the input-contract message. These checks show that the script handles the format; they say nothing about biological sample quality. The empty results/ directory is not tracked by Git unless it contains a file.

Record provenance without overstating reproducibility

Capture the code snapshot used for an analysis after committing the analysis code. The first command writes the current short commit ID; subsequent commands record selected environment details. Because adding these records creates another commit, the saved ID names the code state immediately before the provenance files were committed.

git rev-parse --short HEAD > COMMIT_HASH.txt
python3 --version > ENV_INFO.txt
pip3 freeze > requirements.txt
git add COMMIT_HASH.txt ENV_INFO.txt requirements.txt
git commit -m "Record analysis code revision and Python packages"

pip freeze describes installed Python distributions in the active environment. It does not capture R or Bioconductor packages, operating-system libraries, reference genomes, annotation versions, or external databases. Record those separately when they affect the workflow; use a project-appropriate lockfile or container and test the setup on the intended platform.

Choose how to handle larger files

Keep raw reads and restricted inputs in approved institutional storage. A .gitignore rule only affects untracked paths and does not provide storage, access control, or backup.

  • Git LFS: suitable when collaborators need large files versioned alongside Git and the hosting service's storage and bandwidth limits fit the project. Install/configure LFS, track selected patterns, and commit .gitattributes. Tracking a pattern does not convert copies already present in earlier commits.
  • DVC: can keep data content in configured external storage while Git tracks small metadata files. It requires an appropriately configured remote and permissions; do not point it at a storage location unless the data-use policy permits it.
  • Institutional storage: often the right place for controlled or very large data. Document how authorized collaborators request access and identify the input version without placing restricted data in Git.

Connect to GitHub only after a privacy review

Create an empty remote repository through GitHub's interface, then use its exact clone URL in the commands below. Replace the placeholders and verify the destination before pushing. This optional step writes to a remote account, so it is intentionally not part of the local-only practice run.

git remote add origin https://github.com/USER/REPO.git
git branch -M main
git push -u origin main

GitHub authentication may use HTTPS with an approved credential manager or SSH with a key linked to your account. Do not embed a personal access token in a URL, script, or shell command. Before a public push, inspect git status, review the staged diff, and scan files for likely secrets. A text search is only a screening aid; it cannot prove that a repository is safe to publish.

Read the repository state

  • git status reports staged, modified, and untracked paths. A clean working tree means no uncommitted changes are visible to Git; it does not mean every required file is tracked.
  • git log --oneline --decorate summarizes local history. Focused commits make it easier to identify when a code or configuration change entered the project.
  • git diff --cached shows staged changes. Use it before committing, especially when a broad add command was used.
  • A commit ID records a repository tree and its ancestry. It does not capture an external reference genome, data object, cloud resource, or unrecorded package installation.

A successful script run checks that the script accepted that input. It does not validate the reads, the analysis design, or the biological interpretation. Reproducibility also depends on the input data and versions of dependencies outside Git.

Troubleshoot common problems

Push fails with an authentication error

Check that the remote URL is correct with git remote -v. For SSH, confirm that a key is configured with GitHub and that the SSH agent can access it. For HTTPS, use the credential prompt or your platform's credential manager. Never paste a token into a remote URL to bypass an authentication error.

A supposedly ignored file still appears in Git

Use git check-ignore -v path/to/file to see which rule applies. If the file is already tracked, ignore rules alone will not remove it from the index or history. For a non-sensitive tracked file you intend to keep locally, git rm --cached path/to/file removes it from the index for a future commit. Do not use this as a response to leaked secrets; revoke the credential first and follow your organization's incident process.

A secret or restricted file was committed

Revoke or rotate exposed credentials immediately. Removing a path in a later commit does not remove earlier copies from history. History rewriting can change commit IDs and disrupt collaborators; forks, clones, caches, and backups may retain copies. Follow GitHub's sensitive-data removal guidance and your institutional data-governance process. If personal or clinical data may have been exposed, contact the responsible privacy/security team rather than attempting an improvised cleanup.

The repository grows or clones slowly

Check whether large files entered prior commits. Adding LFS tracking now does not retroactively replace blobs already in history. Moving existing files out of history requires a planned migration and collaborator coordination. For controlled datasets, use an approved external store and document access instead of moving them to a public host.

Practice checklist

  1. Initialize a local repository and explain what Git stores in .git/.
  2. Add a README and reviewed ignore rules; confirm a test path with git check-ignore -v.
  3. Review git diff --cached, make a focused commit, and locate its ID with git log.
  4. Run the example script on a tiny synthetic TSV and verify the missing-header failure.
  5. Before any remote push, check data permissions, inspect staged content, and select an appropriate large-file strategy.

Completion criterion: you can identify the tracked code snapshot, state what the commit does not capture, and explain why ignore rules do not make sensitive files safe.
