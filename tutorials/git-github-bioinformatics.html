Git and GitHub for Bioinformatics

NM

Nasir Mahmood Abbasi, PhD

Bioinformatics Educator

Tested on: Python 3.11, R 4.3.2, Ubuntu 24.04

Learning objectives and prerequisites

By the end of this lesson you will be able to:

  • Create and initialize a local Git repository for a bioinformatics project.
  • Make focused commits, inspect history, and work with branches for safe feature development.
  • Write a practical README and .gitignore that avoid committing sensitive or large raw data.
  • Configure a remote (GitHub) connection safely and push code without leaking secrets.
  • Use Git LFS or DVC to manage large sequencing files outside of Git history.

Prerequisites:

  • Basic comfort using a terminal (bash, zsh, or similar).
  • Git installed locally (see git --version).
  • Optional: a GitHub account if you want to push to a remote repository.

Why Git and GitHub matter in bioinformatics

Bioinformatics analyses are complex: multiple scripts, configuration files, software environments, and sometimes many collaborators. Git provides a precise, timestamped history of how text files (code, configuration, notebooks, small sample data) change over time. That history is the minimal unit for reproducibility: a commit hash identifies the exact code state that produced a result.

GitHub (and similar hosted services) add collaboration features: remote hosting, issues, pull requests for code review, and releases to bundle a particular snapshot for distribution. Together they help you track provenance (what was run and when), enable peer review of analysis code, and reduce accidental sharing of private data.

Important safety notes:

  • Never commit raw patient identifiers, clinical notes, full BAM/FASTQ files, or API credentials into a Git repository.
  • Large raw data should be stored in institutional storage, cloud buckets, or tracked with tools designed for large files (Git LFS or DVC).
  • Consider project policies (institutional review boards, data-sharing agreements) before publishing code or scripts that could re-identify individuals.

Reproducible, sequential workflow

The following steps show a minimal, reproducible project layout. Commands are written with explicit paths and produce predictable files. Replace USER and REPO with your GitHub username and repository name only after confirming no sensitive data are present.

1. Create a project directory and initialize Git

mkdir -p ~/projects/omics-demo
cd ~/projects/omics-demo
git init

Files created / modified:

  • The directory ~/projects/omics-demo is created.
  • .git/ is created as the local repository metadata (hidden).

What this produces: a local empty repository ready to track files.

2. Add a README and a conservative .gitignore

cat > README.md << 'EOF'
# Omics demo

This repository contains example scripts and configuration to illustrate Git best practices
for a bioinformatics analysis. This repo intentionally avoids raw sequencing files.
EOF

cat > .gitignore << 'EOF'
# Raw sequencing and large files
data/raw/
*.fastq.gz
*.bam
*.bai

# Temporary files and python caches
*.pyc
__pycache__/
.ipynb_checkpoints/

# Environment directories
.env
.venv/
envs/

# Credentials and keys
.env.local
*.key
EOF

Files created:

  • README.md — human-readable description and usage notes.
  • .gitignore — prevents common sensitive or large files from being added accidentally.

3. Make a first meaningful commit

git add README.md .gitignore
git commit -m "Initialize project with README and conservative .gitignore"
git log --oneline --decorate -1

What to inspect:

  • git status should report no changes to commit.
  • git log --oneline --decorate -1 prints the most recent commit hash and message; this hash identifies this snapshot.

4. Add a small example script and document inputs/outputs

mkdir -p scripts results
cat > scripts/qc_summary.py << 'EOF'
#!/usr/bin/env python3
# scripts/qc_summary.py
# Example: read a tab-delimited QC summary and print counts per sample.
import sys
import csv

if len(sys.argv) < 2:
    print("Usage: qc_summary.py samples.tsv")
    sys.exit(1)

with open(sys.argv[1]) as fh:
    reader = csv.DictReader(fh, delimiter='\t')
    for row in reader:
        print(row.get('sample', 'NA'), row.get('reads', '0'))
EOF

chmod +x scripts/qc_summary.py
git add scripts/qc_summary.py
git commit -m "Add small QC summary script with documented input format"

Files and outputs:

  • scripts/qc_summary.py — an executable example script. It documents expected input (a TSV with a "sample" and "reads" column).
  • results/ — a directory to hold generated figures or processed outputs (left empty in this step).

5. Tagging and capturing the environment

Record the software environment and the commit hash you used to generate results. This is essential for later reproducibility.

# record the short commit hash
git rev-parse --short HEAD > COMMIT_HASH.txt

# record Python and pip versions (example)
python3 --version > ENV_INFO.txt
pip3 freeze > requirements.txt

git add COMMIT_HASH.txt ENV_INFO.txt requirements.txt
git commit -m "Record commit hash and environment information"

What these files contain:

  • COMMIT_HASH.txt — the unique identifier of the repository state.
  • ENV_INFO.txt and requirements.txt — exported software environment details to help reproduce the analysis later.

6. Configure a remote GitHub repository safely

When you are ready to publish non-sensitive code to GitHub, set up a remote. Use HTTPS with a credential manager or SSH keys; do NOT hard-code personal access tokens into commands, scripts, or environment files.

# Example remote setup (HTTPS). Replace USER and REPO.
git remote add origin https://github.com/USER/REPO.git
git branch -M main
git push -u origin main

Alternatives and safety reminders:

  • Prefer SSH: git remote add origin git@github.com:USER/REPO.git (requires an SSH key associated with your GitHub account).
  • Never put tokens in a URL like https://TOKEN@github.com/... — this can leak to shell history and CI logs.

Output inspection and interpretation

After following the workflow above, check the following and interpret what they mean (and do not mean):

  • git status should show a clean working tree if you've committed all changes. Clean status means your local text files are fully captured by Git, not that the analysis itself is correct.
  • git log --oneline --decorate shows the sequence of commits. Each commit message should correspond to a single logical change — this makes it possible to find the commit that introduced a change later.
  • COMMIT_HASH.txt stores a unique identifier. The presence of this file allows you to link a published result (paper, figure) to an exact code snapshot. It does not guarantee that the environment recorded will reproduce the result unless versions of non-Python dependencies (R, system libraries, reference genomes) are also captured.
  • .gitignore ensures that large or sensitive files are not accidentally added. However, if a file was committed before it was added to .gitignore, the history still contains that file. Removing sensitive data from history requires special procedures (see Troubleshooting).

What a plausible result looks like (example checks):

  • Running scripts/qc_summary.py samples.tsv prints sample names and read counts — this verifies the script runs but does not verify data quality.
  • After pushing, the remote repository on GitHub shows the README, commit history, and files you expect. If files are missing, check git push output for errors (authentication, protected branches).

What this does NOT prove:

  • That your analysis produced biologically valid results. Git documents provenance, not correctness.
  • That a given environment will run identically on a different machine unless all dependencies (including system libraries and reference data versions) are captured and tested.

Troubleshooting: symptoms, causes, and fixes

Symptom: "git push" fails with authentication errors

Likely causes:

  • No SSH key is configured, or the SSH agent is not running.
  • Credential manager mis-configuration for HTTPS.

Fixes:

  • Use SSH: generate a key with ssh-keygen -t ed25519 -C "your.email@institution.edu", add the public key to GitHub, and test with ssh -T git@github.com.
  • For HTTPS, ensure a credential helper is configured (git config --global credential.helper), or use your operating system's credential prompt rather than embedding tokens in commands.

Symptom: Sensitive file accidentally committed

Likely causes:

  • A secret was present before a .gitignore rule was added.

Fixes and cautions:

  • Remove the file from history using the BFG Repo-Cleaner or git filter-repo. Follow upstream guides carefully. After rewriting history you must force-push and coordinate with collaborators; this invalidates old commit hashes.
  • Change any leaked credentials immediately (rotate tokens, change passwords) because even after removal they may persist in forks or cached mirrors.

Symptom: Large files make the repository slow

Likely causes:

  • Raw FASTQ or BAM were committed into the Git history.

Fixes:

  • Use Git LFS for moderate-sized files (track filetypes with git lfs track "*.bam"), then add and commit the .gitattributes file. See official Git LFS docs.
  • For large datasets, use DVC (Data Version Control) to track large files in external storage while keeping small pointer files in Git.

Limitations, version and reference-data caveats, and responsible use

Limitations:

  • Git is designed to track changes to text files efficiently. It does not manage very large binary files well without extensions like Git LFS or DVC.
  • Commit hashes are stable for a repository only; rewriting history (force pushes) changes hashes and can complicate reproducibility unless carefully coordinated.

Version and reference-data caveats:

  • Record versions of reference genomes, annotation files (GTF/GFF), and index files. These are often updated, and differences can materially change results.
  • System libraries (C/C++ runtime versions), R and Bioconductor package versions, and container images all affect reproducibility. Where feasible, capture a container (Docker/Singularity) or an explicit environment export (e.g., conda env export or renv.lock for R).

Responsible use:

  • Do not publish code or metadata that could re-identify individuals. Before sharing, remove or generalize identifiers and consult data-use agreements.
  • When using third-party datasets, respect licensing and citation requirements.

Next-step checklist

  • Make sure your repository contains: README.md, .gitignore, small example scripts, and a file recording COMMIT_HASH.txt and environment details.
  • Decide how to handle large data: add Git LFS for intermediate outputs or configure DVC for raw data stored externally.
  • Establish a branching strategy (e.g., main for stable code, feature branches for work in progress).
  • Write CONTRIBUTING.md and a basic code of conduct if you expect external collaborators.
  • Before pushing to a public remote, run git status and git grep -n --hidden -I 'PASSWORD\\|TOKEN\\|SECRET' (or an equivalent scan) to check for accidental secrets. If in doubt, do not push and consult your data governance officer.

References

  • GitHub Docs — official guidance on remotes, SSH keys, and GitHub workflows (pull requests, issues).
  • Git LFS — tools and documentation for tracking large binary files with Git.
  • DVC (Data Version Control) — documentation for versioning large datasets and connecting to remote storage.
  • “Ten Simple Rules for Reproducible Computational Research” — principles that complement careful version control.
